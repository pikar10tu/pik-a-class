## 1. การจัดการ Layer และ Stacking Context (Modal & Z-index)
- **ปัญหาที่เคยพบ (2026-09-23):** 
  เมื่อคลิกที่ด่านเพื่อเปิดหน้าต่าง Bottom Sheet สรุปด่าน ปรากฏว่าวงกลมด่าน (`.path-node`) และเส้นทางสีเขียว (`.path-track-done`) ลอยทะลุขึ้นมาทับบนหน้าต่าง Sheet จนข้อความด้านหลังถูกบัง
- **สาเหตุทางเทคนิค:**
  - `<main class="learn-main">` ถูกตั้งค่า `position: relative; z-index: 1;`
  - กล่อง `.path-canvas` มีการใช้ `backdrop-filter: blur(...)` ซึ่งสร้าง Stacking Context ใหม่
  - ในขณะที่ `.sheet-backdrop` (ม่านดำของ Modal) มีเพียง `position: fixed` แต่**ไม่มีการระบุ `z-index`** (ทำให้มีค่า default เป็น `auto` หรือเทียบเท่า 0)
  - เบราว์เซอร์จึงวาด `<main>` (z-index: 1) ทับบน `.sheet-backdrop` (z-index: 0)
  - นอกจากนี้ `.sheet` เดิมใช้ `background: var(--color-bg)` ซึ่งอาจโปร่งหรือกลืนกับพื้นหลัง
- **กฎเหล็กเพื่อป้องกันไม่ให้เกิดซ้ำ:**
  1. ทุกองค์ประกอบที่เป็น Modal, Bottom Sheet, Backdrop, หรือ Popover ต้องกำหนด `z-index: 1000+` เสมอ
  2. ตัวกล่องเนื้อหาภายใน Sheet (`.sheet`) ต้องกำหนดพื้นหลังเป็นสีทึบชัดเจน เช่น `background: var(--color-surface, #ffffff);` และกำหนด `z-index: 1001;` เสมอ เพื่อไม่ให้สิ่งที่อยู่ข้างหลังมองทะลุขึ้นมาได้
  3. ห้ามปล่อยให้ Overlay element ไม่มี `z-index` เด็ดขาด

## 2. การกำหนดสีพื้นหลังและความชัดเจน (Contrast & Visual Visibility)
- **ปัญหาที่เคยพบ:** 
  กำหนดสี Gradient พาสเทลเป็น `#f0fdf4` ถึง `#f8fafc` ซึ่งมีความสว่าง (Lightness) สูงกว่า 96% เมื่อมองบนหน้าจอสมาร์ตโฟนหรือจอคอมทั่วไป จะดูกลมกลืนจนมองเป็นสีขาวล้วน
- **สาเหตุทางเทคนิค:**
  - สีพาสเทลที่เจือจางเกินไปจะสูญเสีย Saturation
  - การพึ่งพา CSS Selector `:has()` เพียงอย่างเดียว เช่น `body:has(.learn-main)` อาจไม่ทำงานในเบราว์เซอร์บางรุ่น หรือถูก override โดย `base.css`
- **กฎเหล็กเพื่อป้องกันไม่ให้เกิดซ้ำ:**
  1. สีพื้นหลังฉากต้องเลือกเฉดสีที่มี Saturation ชัดเจน เช่น ฟ้าพาสเทลสดใส `#bae6fd`, เขียวมิ้นต์ `#d1fae5` ไม่ใช่สีที่ใกล้เคียงขาว
  2. ในไฟล์ CSS เฉพาะหน้า (เช่น `learn.css`) ให้ระบุ `body { background: ... !important; }` ชัดเจน เพื่อไม่ให้ `base.css` ที่โหลดมาก่อนหน้ากลบทับ

## 3. การวางตำแหน่ง Pseudo-elements บน Body (`body::before` / `body::after`)
- **ปัญหาที่เคยพบ:** 
  ตั้งค่าก้อนเมฆ `body::before { z-index: -1; }` แล้วก้อนเมฆหายไป ไม่แสดงผล
- **สาเหตุทางเทคนิค:**
  - ในมาตรฐาน CSS การตั้ง `z-index: -1` บน pseudo-element ของ `body` จะทำให้ element นั้นถูกเรนเดอร์อยู่**หลังระนาบพื้นหลังของ body เอง** (Behind body canvas) จึงโดนสีพื้นหลังของ body กลบมิด
- **กฎเหล็กเพื่อป้องกันไม่ให้เกิดซ้ำ:**
  1. Pseudo-element ของฉากหลัง (เช่น ก้อนเมฆ หรือเนินเขา) ต้องตั้ง `z-index: 0`
  2. ตัวเนื้อหาหลัก (`.learn-main`, `.dashboard-main`) ให้ตั้ง `position: relative; z-index: 1;` เพื่อให้ลอยอยู่เหนือก้อนเมฆเสมอ

## 4. ปุ่ม Action หน้าจอสรุปผลจบด่าน (Result Screen Button Hierarchy)
- **ปัญหาที่เคยพบ:** 
  เมื่อเด็กทำข้อสอบผ่านด่าน ปุ่มเด่น (`btn-chunky`) ยังคงเป็น "เล่นด่านนี้อีกครั้ง" ทำให้เด็กเผลอกดซ้ำ แทนที่จะได้ก้าวต่อไปด่านใหม่
- **กฎเหล็กเพื่อป้องกันไม่ให้เกิดซ้ำ:**
  1. **กรณีผ่านด่าน (`summary.passed == true`):**
     - ปุ่มหลัก (เด่นสุด, สีเขียว `btn-chunky`) = **"ไปต่อ"** (พากลับแผนที่ด่านเพื่อเข้าด่านใหม่) และต้องวางไว้ด้านบน
     - ปุ่มรอง (`btn-ghost`) = **"เล่นด่านนี้อีกครั้ง"**
  2. **กรณีไม่ผ่านด่าน (`summary.passed == false`):**
     - ปุ่มหลัก = **"ลองอีกครั้ง"**
     - ปุ่มรอง = **"กลับเส้นทางด่าน"**

## 5. ความสอดคล้องระหว่าง Firestore Security Rules กับ Client Queries
- **ข้อควรระวัง:** 
  Firestore Security Rules **ไม่ใช่ตัวกรอง (Rules are not filters)**
  หากใน Rules มีการตรวจ `resource.data.level in myUserDoc().allowedLevels` แต่ Query ฝั่ง Client ไม่ได้ระบุ `where('level', '==', level)` Firestore จะปฏิเสธการอ่านทั้งชุด (Permission Denied) ทันที
- **กฎเหล็กเพื่อป้องกันไม่ให้เกิดซ้ำ:**
  1. ทุก Query ที่ดึงข้อมูล Exercises หรือ Stages ต้องมีเงื่อนไข `level` ที่ชัดเจนตรงกับสิทธิ์ของผู้เรียน
  2. ก่อน Deploy Rules ใหม่ ต้องทดสอบด้วย `npm run test:rules` เสมอ

## 6. กฎการผลิตเนื้อหาหลักสูตรครบวงจร (Content & Grammar Notes Integrity)
- **ปัญหาที่เคยพบ (2026-09-23):**
  เมื่อสร้างข้อสอบและด่านเสร็จ แต่ไม่ได้เพิ่มสรุปไวยากรณ์ (Grammar Notes) ให้ครบทุกแท็กพร้อมกันในคราวเดียว (เช่น เคยตกหล่น `grammar:present-continuous`) ทำให้นักเรียนกดดูสรุปก่อนเริ่มด่านแล้วไม่มีคำอธิบายโชว์ และต้องย้อนกลับมาตามแก้ซ้ำซ้อน
- **กฎเหล็กเพื่อป้องกันไม่ให้เกิดซ้ำ (บังคับใช้กับ A2 ส่วนที่เหลือ, B1, B2 เป็นต้นไป):**
  1. **ทำเนื้อหาแบบ All-in-One Package:** ทุกครั้งที่ผลิตระดับใหม่ ต้องทำพร้อมกันครบทั้ง 3 เสาหลักในรอบเดียวเสมอ:
     - **เสาที่ 1 — สรุปไวยากรณ์ (Grammar Notes):** เขียนลงใน `src/lib/grammar-notes.js` ครบทุกแท็ก โดยมีครบทั้ง 4 มิติ: คอนเซปต์ (concept), โครงสร้างประโยค (formula), ตัวอย่างประโยค (examples), และทริกสำคัญดักหลุมพรางเด็กไทย (tips)
     - **เสาที่ 2 — คลังข้อสอบ (Exercises):** ครบ 15 ข้อต่อโมดูล (Duolingo Sentence Builder 4 ข้อ, เติมคำ Fill-in-the-Blank 5 ข้อ, 4 ตัวเลือก MCQ 6 ข้อ)
     - **เสาที่ 3 — เส้นทางด่าน (Stages):** จัดแบบ Spiral Learning ครบ 20 ด่าน (คู่ด่าน Part 1 & 2, มินิบอส Stage 10, บอสใหญ่ Stage 20)
  2. **รัน Automated Verification ทุกแท็ก:** มีคำสั่งตรวจเช็กว่าทุกแท็กที่ระบุใน Taxonomy สามารถดึง Grammar Note ได้สำเร็จ 100% ก่อนนำเข้าสู่ Firestore จริง

## 7. การออกแบบตัวเลือกคำแปลและป้องกันการบอกใบ้เฉลย (Anti-Guessing & Choice Sanitization)
- **ปัญหาที่เคยพบ (2026-09-23):**
  ในคลังคำศัพท์เดิมและมินิเกม Pik Speed Cafe ตัวเลือกเฉลยบางข้อมีคำแปล 2 ความหมายหรือมีวงเล็บขยายความ เช่น `กระหายน้ำ, หิวน้ำ` หรือ `ส่วนผสม, วัตถุดิบ` ขณะที่ตัวเลือกหลอก 3 ข้อเป็นคำเดี่ยวสั้นๆ ส่งผลให้เด็กสังเกตเห็นความผิดปกติของข้อสอบ (Test-wiseness) แล้วเลือกข้อที่ยาวกว่าหรือมีเครื่องหมายจุลภาคทันทีโดยไม่อ่านคำศัพท์ภาษาอังกฤษ
- **กฎเหล็กเพื่อป้องกันไม่ให้เกิดซ้ำ:**
  1. **คำแปลต้องเป็นคำเดี่ยวกระชับ:** ทุกคำศัพท์ใน `thai:` และ `alternatives:` ต้องเป็นคำแปลเดี่ยว ไม่ยาวเกินไป ไม่ใส่เครื่องหมายจุลภาค `,` หรือวงเล็บ `(...)`
  2. **ระดับความยาวและชนิดของคำต้องสมดุล:** ตัวเลือกหลอกทั้ง 3 ข้อต้องเป็น Part of Speech เดียวกัน และมีความยาวคำใกล้เคียงกับเฉลยเสมอ
  3. **มี Sanitizer ใน Game Engine:** โค้ดฝั่งสร้างตัวเลือก (เช่น `cafe-engine.js`) ต้องมีฟังก์ชัน `sanitizeChoiceText()` ตัดแต่งเฉพาะคำแปลหลักก่อนส่งไปแสดงผลบนปุ่มตัวเลือกเสมอ
  4. **มี Unit Test บังคับตรวจ:** เขียน Vitest กำกับว่าคำศัพท์และตัวเลือกทุกคำในระบบต้องไม่มีเครื่องหมาย `,`, `()`, หรือ `/` อย่างเด็ดขาด

## 8. ขนาดคลังคำศัพท์และจิตวิทยาการเรียนรู้ของเด็ก (Vocab Sizing for Spaced Repetition)
- **บทเรียนเชิงการศึกษา (Pedagogical Insight):**
  - หากคำศัพท์ต่อหมวดน้อยเกินไป (เช่น 4–7 คำ): เมื่อเด็กเลือกฝึกเฉพาะระดับ (เช่น A1 ในหมวดอาหาร) จะมีคำศัพท์เพียง 1–2 คำ เล่นรอบเดียวก็ซ้ำ ทำให้เด็กจำตำแหน่งช้อยส์แทนจำความหมาย
  - หากคำศัพท์มากเกินไปในขั้นแรก (50+ คำต่อหมวด): เกิด Cognitive Overload เด็กจะท้อแท้ และการสุ่มจะไม่วนกลับมาเจอคำเดิมในระยะเวลาที่เหมาะสม ทำให้ลืมคำแรกไปก่อน
- **กฎเกณฑ์มาตรฐานของโปรเจกต์:**
  1. **เป้าหมายขนาดคลังคำศัพท์:** กำหนดมาตรฐานที่ **20–25 คำต่อหมวด** (รวม 9 หมวด = ~200–225 คำ)
  2. **กระจายตามระดับ CEFR:** แบ่งสัดส่วน A1 (7 คำ), A2 (7 คำ), B1 (5 คำ), B2 (5 คำ) ในทุกหมวด
  3. **เหมาะกับช่วงสมาธิ (Micro-learning):** สอดคล้องกับรอบเกม 10–15 ข้อ เล่นได้ 2 รอบไม่ซ้ำ และผู้เรียนระดับเริ่มต้น (A1) จะมีคำศัพท์หมุนเวียนรวมถึง ~60 คำ

## 9. การลงทะเบียนหน้าเว็บใหม่ในระบบ Vite Multi-Page Application (MPA)
- **ปัญหาที่อาจเกิดขึ้น:**
  สร้างไฟล์ HTML ใหม่ในโฟลเดอร์ย่อย (เช่น `src/vocab/index.html`, `src/vocab/cafe.html`, `src/admin/student-report.html`) แล้วพบว่าเมื่อรัน `npm run build` หน้าดังกล่าวไม่ถูกรวมลงในโฟลเดอร์ `dist/` หรือ Service Worker ไม่ได้ทำการ Precache หน้านั้น
- **กฎเหล็กเพื่อป้องกันไม่ให้เกิดซ้ำ:**
  1. ทุกครั้งที่เพิ่มหน้า HTML ใหม่ ต้องเปิด [`vite.config.js`](file:///d:/WEBPROJECT/pik-a-class/vite.config.js) และลงทะเบียนหน้านั้นลงใน `build.rollupOptions.input` ทันที
  2. หลังลงทะเบียน ต้องรัน `npm run build` เสมอเพื่อตรวจสอบว่าหน้าใหม่ถูกแพ็กและนับรวมใน Workbox precache เรียบร้อย

## 10. สถาปัตยกรรมการเก็บสถิติการทำซ้ำและรายงานผู้ปกครอง (Repetition Tracking & Parent Report Card)
- **สถาปัตยกรรมข้อมูล (Data Architecture):**
  - ความก้าวหน้าของเด็กไม่วัดแค่ "ผ่านหรือไม่ผ่าน" แต่วัดที่ **"จำนวนการทำซ้ำ (Repetitions) และความพยายาม"**
  - ทุกการทำข้อสอบ (ผ่านด่าน หรือ เล่นมินิเกมคำศัพท์) จะต้องบันทึกเข้า Firestore Collection `submissions` โดยมีฟิลด์:
    - `attemptCount`: นับจำนวนครั้งที่ทำซ้ำ
    - `wrongCount`: นับจำนวนข้อที่ตอบผิด
    - `skill`: ระบุประเภททักษะ (`vocab` | `grammar` | `dialogue`)
    - `level`: ระบุระดับ CEFR (`A1` - `B2`)
  - หน้า Parent Report Card (`src/admin/student-report.html`) ออกแบบพร้อมปุ่ม 1-Click Export 3 รูปแบบ:
    1. **บันทึกภาพ PNG (html2canvas):** สำหรับส่งรูปทางแชต
    2. **คัดลอกข้อความสรุป:** ข้อความฟอร์แมตกระชับ มีอีโมจิ สำหรับส่งผ่าน LINE ให้ผู้ปกครอง
    3. **พิมพ์รายงาน / บันทึก PDF:** สำหรับพิมพ์เป็นเอกสารผลการเรียนจริง
