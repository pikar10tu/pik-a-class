# Admin Usability — Design Spec

> ต่อยอดจาก sub-project 2 (`docs/superpowers/specs/2026-09-20-data-layer-design.md`) — บันทึกวันที่ 2026-09-20
> เกิดจากการใช้งานจริง: ปิ๊กลองใช้หน้า admin แล้วบอกว่า "tool มันใช้ยากมาก"

## 1. ขอบเขต (Scope)

ทำให้เครื่องมือฝั่ง admin **ใช้งานได้โดยไม่ต้องจำรูปแบบข้อมูล** — ปัญหาปัจจุบันคือผู้ใช้ต้องรู้ว่า tag ชื่อเต็มคืออะไร ต้องพิมพ์ตัวเลือกคั่นด้วยจุลภาคเอง และต้องพิมพ์เฉลยให้ตรงกับตัวเลือกเป๊ะๆ ด้วยมือ

จบ sub-project นี้แล้วต้องทำสิ่งเหล่านี้ได้จริง:

1. ปิ๊กสร้างโจทย์ใหม่ได้จากในเว็บโดยไม่ต้องแตะ JSON เลย
2. แก้โจทย์เดิมโดยเลือกเฉลยจากตัวเลือกที่มีอยู่จริง และเลือก tag จากรายการ (พิมพ์ผิดไม่ได้)
3. ลบโจทย์ได้ พร้อมกล่องยืนยันที่เห็นเนื้อโจทย์ก่อนลบ
4. หน้าคลังเนื้อหาสแกนด้วยตาได้ — เห็นว่ามีข้ออะไรบ้างโดยไม่ต้องเลื่อนผ่านฟอร์มของทุกข้อ

**ไม่อยู่ในขอบเขตนี้:** ดีไซน์ (สี/ฟอนต์/visual direction — ปิ๊กเลือกพักไว้ก่อน), โจทย์ชนิด `matching` และ `shadowing`, ฟอร์มแก้ `stages`/`grammarNotes` (ยังใช้ JSON), UI ฝั่งนักเรียน, การแก้ security rules (ไม่จำเป็น — rules รอบที่แล้วอนุญาตให้ admin สร้าง/แก้/ลบได้อยู่แล้ว)

## 2. การตัดสินใจที่ยืนยันแล้ว

| เรื่อง | มติ | เหตุผล |
|---|---|---|
| ขอบเขตงานหน้าตา | **พักดีไซน์ไว้ ทำเฉพาะ usability** | ปิ๊กเลือกเอง — แก้ให้ใช้งานได้ก่อน ค่อยว่ากันเรื่องสวย |
| ความอ่านง่าย | ปรับผ่าน **โครงสร้าง** (จัดกลุ่มฟิลด์, ป้ายกำกับ, ระยะห่าง) โดยใช้ token เดิมใน `tokens.css` ไม่ตั้งสี/ฟอนต์ใหม่ | "อ่านยาก ไม่รู้ว่าอะไรอยู่ตรงไหน" ส่วนใหญ่เป็นปัญหาโครงสร้าง ไม่ใช่รสนิยม |
| ชนิดโจทย์ที่ฟอร์มรองรับ | `mcq`, `fill_blank`, `short_answer`, `paragraph` | 4 ชนิดที่ core loop และการบ้านใช้จริง — `matching`/`shadowing` ยังไม่มี UI ฝั่งนักเรียน ออกแบบฟอร์มตอนนี้จะเดาผิด |
| โครงหน้าจอ | **หน้าแก้ไขแยกต่างหาก** ใช้ทั้งสร้างใหม่และแก้ | หน้ารายการเบาลงและสแกนได้, ปุ่ม back ของเบราว์เซอร์ทำงานถูก, บนมือถือไม่อึดอัดเหมือน modal |
| หน้านำเข้า JSON | คงไว้ ไม่แตะ | ฟอร์มทีละข้อไม่ได้มาแทน — ตอน generate เนื้อหาเป็นร้อยข้อยังต้องใช้ JSON |

## 3. โครงหน้าจอ

```
admin/content.html          รายการอย่างเดียว (ย้ายฟอร์มออกทั้งหมด)
  [ตัวกรอง: สถานะ | สกิล | เลเวล]      ← เปลี่ยนแล้วโหลดเอง ไม่มีปุ่ม "โหลด"
  [+ สร้างโจทย์ใหม่]
  ┌────────────────────────────────────────┐
  │ draft · grammar A1 · MCQ               │
  │ She ___ to school every day.           │
  │ grammar:present-simple                 │
  │ [แก้ไข] [อนุมัติ] [ลบ]                  │
  └────────────────────────────────────────┘

admin/exercise.html         ฟอร์มเต็มทีละข้อ
  ?id=<docId> → โหมดแก้ไข        ไม่มี id → โหมดสร้างใหม่
```

หน้ารายการแสดงต่อข้อ: สถานะ, skill + level + ชนิด, ข้อความโจทย์ (ตัดถ้ายาวเกิน 120 ตัวอักษร), tag ทั้งหมด และปุ่ม 3 ปุ่ม ไม่มีฟอร์มฝังอยู่อีกต่อไป

## 4. ฟอร์มสร้าง/แก้โจทย์

เลือก **ชนิดโจทย์ก่อน** แล้วฟอร์มเปลี่ยนตามชนิด:

| ชนิด | ฟิลด์ที่แสดง |
|---|---|
| `mcq` | โจทย์ + ตัวเลือกแยกช่องละตัว (ปุ่ม "เพิ่มตัวเลือก" / "ลบตัวเลือก") + **radio หน้าแต่ละตัวเลือกเพื่อเลือกข้อที่ถูก** |
| `fill_blank` | โจทย์ + ปุ่ม "แทรกช่องว่าง `___`" (แทรกตรงตำแหน่งเคอร์เซอร์) + "คำตอบที่รับได้" แยกช่องละคำตอบ เพิ่มได้หลายคำตอบ |
| `short_answer`, `paragraph` | โจทย์ + เกณฑ์ให้คะแนน (rubric) — ซ่อนตัวเลือก/เฉลยทิ้งทั้งหมด |

ทุกชนิดมีร่วมกัน: สกิล, เลเวล, tag, `isPreview`, `visibility`, สถานะ (`reviewStatus`)

**การเลือก tag:** เป็น checkbox จัดกลุ่มไวยากรณ์/คำศัพท์ แสดงเฉพาะ tag ที่เลเวลไม่สูงกว่าเลเวลของข้อ (กฎเดียวกับ `checkTagsForLevel`) — เปลี่ยนเลเวลแล้วรายการ tag อัปเดตตาม และ tag ที่เลือกไว้แล้วแต่สูงเกินเลเวลใหม่จะถูกถอดออกพร้อมข้อความบอก

**การแสดง error:** ข้อความจาก `validate()` ไปแสดง**ใต้ฟิลด์ที่ผิด** (map จาก `error.field` ไปยัง input) ส่วน error ที่ไม่ตรงกับฟิลด์ไหนเลยไปรวมไว้ท้ายฟอร์ม

**พรีวิว:** แสดง "สิ่งที่นักเรียนจะเห็น" (ใช้ `previewLines()` เดิม) อัปเดตสดขณะพิมพ์

**การสลับชนิดโจทย์ตอนแก้ข้อเดิม:** ฟิลด์ที่ไม่เกี่ยวกับชนิดใหม่จะถูกล้าง (เช่น MCQ → paragraph ทิ้ง `choices`/`answerKey`) — ต้องมีข้อความยืนยันก่อนล้าง

**ฟิลด์ที่ระบบเติมให้เอง (ฟอร์มไม่แสดง):** `contentHash` (คำนวณจากโจทย์+ตัวเลือกเหมือนตอนนำเข้า), `createdAt`/`updatedAt`, `createdBy` (uid ของ admin ที่กดบันทึก), `assignedUids` (ค่าเริ่มต้น `[]`) — ใช้ตัวช่วยชุดเดียวกับหน้านำเข้า JSON เพื่อไม่ให้สองทางเขียนข้อมูลต่างรูปแบบกัน

**หลังบันทึก:** โหมดสร้างใหม่บันทึกเป็น `reviewStatus: draft` เสมอ แล้วเด้งกลับหน้ารายการพร้อมข้อความยืนยัน; โหมดแก้ไขอยู่หน้าเดิมและแสดงว่าบันทึกแล้ว

## 5. การลบ — มีถังขยะคั่นหนึ่งขั้น

**ทิ้งลงถัง (ขั้นปกติ):** ปุ่ม "ทิ้ง" อยู่ทั้งในรายการและในหน้าแก้ไข → กล่องยืนยันแสดง **ข้อความโจทย์เต็ม** + สถานะปัจจุบัน → กดยืนยันแล้วระบบเขียน 2 อย่างพร้อมกัน:

```
deletedAt: <เวลาปัจจุบัน>
reviewStatus: "draft"      ← บังคับเสมอ
```

**เหตุผลที่ต้องบังคับ `draft` ด้วย:** security rules ตัดสินว่านักเรียนเห็นเนื้อหาไหมจาก `reviewStatus` เพียงอย่างเดียว ถ้าทิ้งข้อที่ `published` ลงถังโดยไม่เปลี่ยนสถานะ นักเรียนจะยังเห็นข้อที่ถูกทิ้งไปแล้ว — ทิ้งแล้วต้องหายจากสายตานักเรียนทันที

**หน้าถังขยะ** (`admin/content.html?trash=1` ใช้หน้าเดิม สลับด้วยปุ่ม "ดูถังขยะ"): แสดงเฉพาะข้อที่มี `deletedAt` เรียงจากที่ทิ้งล่าสุด พร้อม 2 ปุ่มต่อข้อ
- **กู้คืน** — ล้าง `deletedAt` ทิ้ง ข้อกลับไปอยู่ในคลังสถานะ `draft` (ไม่กลับไป published เอง ปิ๊กต้องกดอนุมัติใหม่ ซึ่งถูกต้องเพราะควรได้ตรวจอีกรอบ)
- **ลบถาวร** — ลบเอกสารจริง กล่องยืนยันบอกตรงๆ ว่ากู้คืนไม่ได้อีก

**ของในถังไม่โผล่ในคลังเนื้อหาปกติ** — หน้ารายการกรองข้อที่มี `deletedAt` ออก ส่วนหน้าถังใช้ query `where('deletedAt', '!=', null)` ซึ่ง Firestore จะคืนเฉพาะเอกสารที่มีฟิลด์นี้จริง

ไม่มีการล้างถังอัตโนมัติตามเวลา — ของค้างในถังไม่กระทบใคร (นักเรียนมองไม่เห็นอยู่แล้ว) จะเพิ่มทีหลังเมื่อจำเป็นก็ได้

**ผลกระทบต่อ security rules:** ต้องเพิ่ม `deletedAt` เข้า allowlist ของ `exercises` ใน `firestore.rules` แล้ว deploy ใหม่ (`npx firebase deploy --only firestore`) — เป็นการแก้ rules ครั้งเดียวของ sub-project นี้

## 6. ไฟล์ที่เกี่ยวข้อง

**สร้างใหม่:**
- `src/admin/exercise.html` + `exercise.js` — หน้าฟอร์ม
- `src/lib/exercise-form.js` — ตรรกะฟอร์มล้วนๆ ไม่แตะ DOM/Firebase (ประกอบ object จากสถานะฟอร์ม, ล้างฟิลด์ตอนสลับชนิด, กรอง tag ตามเลเวล)
- `src/lib/exercise-form.test.js`

**แก้ของเดิม:**
- `src/admin/content.html` + `content.js` — ถอดฟอร์มออก เหลือรายการ + ปุ่ม, โหลดอัตโนมัติเมื่อเปลี่ยนตัวกรอง, เพิ่มปุ่มทิ้ง/สลับมุมมองถังขยะ
- `src/lib/admin-content-io.js` — เพิ่ม `fetchExercise(db, id)`, `createExercise(db, item)`, `trashExercise(db, id)`, `restoreExercise(db, id)`, `deleteExercise(db, id)`, `fetchTrashedExercises(db)`
- `src/lib/schema/exercises.js` — เพิ่มฟิลด์ `deletedAt` (optional, ISO date)
- `firestore.rules` — เพิ่ม `deletedAt` เข้า allowlist ของ `exercises` แล้ว deploy ใหม่
- `firestore.indexes.json` — เพิ่ม index สำหรับ query ถังขยะถ้า Firestore ขอ
- `src/lib/admin-content.js` — `buildContentUpdate()` เดิมถูกแทนที่ด้วยตรรกะใน `exercise-form.js` (ย้าย `previewLines()` ไปไว้ที่เดียวกัน) และ `src/lib/admin-content.test.js` ต้องย้ายเคสที่ยังใช้ได้ไปอยู่กับโมดูลใหม่ ไม่ทิ้งความครอบคลุมเดิม
- `src/lib/admin-nav.js` — ไม่ต้องเพิ่มเมนู (หน้าฟอร์มเข้าจากหน้าคลังเนื้อหาเท่านั้น)
- `vite.config.js` — เพิ่ม entry ของหน้าใหม่
- `src/styles/base.css` — คลาสสำหรับรายการและฟอร์ม (ใช้ token เดิม)

## 7. การทดสอบ

**Unit test (vitest):** ตรรกะใน `exercise-form.js` ทั้งหมด — ประกอบ object จากสถานะฟอร์มแล้วผ่าน `validate()`, เลือกเฉลยจาก radio แล้วได้ `answerKey` ที่อยู่ใน `choices` เสมอ, สลับชนิดแล้วฟิลด์ที่ไม่เกี่ยวถูกล้าง, รายการ tag ที่เลือกได้เปลี่ยนตามเลเวล, tag ที่สูงเกินถูกถอดออกเมื่อลดเลเวล

**Rules test:** ชุดเดิม 25 เคสต้องยังผ่าน + เพิ่มเคสของถังขยะ — admin เขียน `deletedAt` ได้, นักเรียนเขียนไม่ได้ (เหมือนฟิลด์อื่นของ `exercises`), และข้อที่ถูกทิ้ง (มี `deletedAt` + `reviewStatus: draft`) นักเรียน tier `full` อ่านไม่ได้

**ตรวจด้วยมือก่อนปิดงาน:** สร้างโจทย์ MCQ ใหม่ในเว็บจริง → ตรวจว่าเลือกเฉลยผิดจากตัวเลือกไม่ได้ → บันทึกแล้วเห็นในรายการเป็น draft → แก้เป็นเติมคำแล้วยืนยันว่าตัวเลือกถูกล้าง → ทิ้งลงถัง → เปิดถังขยะเห็นข้อนั้น → กู้คืน → ทิ้งอีกครั้งแล้วลบถาวร

## 8. ของที่ต้องส่งมอบเพิ่มเมื่อจบ sub-project นี้

**ดราฟต์ภาพรวมทั้งเว็บ** (ปิ๊กขอไว้) — หน้าเดียวที่ไล่ให้เห็นว่าระบบจะมีหน้าจออะไรบ้างทั้งฝั่งนักเรียนและฝั่ง admin, แต่ละหน้ากดอะไรได้, เชื่อมกันยังไง และอะไรทำแล้ว/ยังไม่ได้ทำ เพื่อตรวจสอบว่าเข้าใจทิศทางตรงกันก่อนเริ่ม sub-project 3 (core loop ฝั่งนักเรียน)

เป็นภาพ **โครงสร้างและฟังก์ชัน** ไม่ใช่สี/ฟอนต์สุดท้าย — และเป็นจังหวะที่เหมาะจะตัดสินใจเรื่อง visual direction ของฝั่งนักเรียน เพราะจะเห็นภาพรวมครบแล้ว
