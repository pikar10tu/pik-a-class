## 1. ที่มาและสิ่งที่เปลี่ยนจาก PLAN เดิม

`PLAN.md` §15 วางลำดับไว้ว่า ข้อ 3 = แบบฝึกหัดอิสระ (auto-grade) แล้วค่อยทำ ข้อ 6 = โซนตะลุยด่าน ทีหลัง

ระหว่าง brainstorm ปิ๊กตัดสินใจ **รวมสองข้อนี้เข้าด้วยกันและทำ "ด่าน" ก่อน** เหตุผลคือเรื่องดาว: ถ้าให้ดาวต่อข้อจากคลังที่สุ่มได้ไม่จำกัด ตัวเลขดาวจะโตไปเรื่อยๆ อย่างไร้ความหมาย แต่ถ้าดาวผูกกับ **ด่านที่มีข้อคงที่** ดาวจะมีเพดาน (3 ดาวต่อด่าน) เล่นซ้ำได้คะแนนดีขึ้นก็แค่ทับค่าเดิม กลายเป็นวงจร "ไล่เก็บดาว" ที่จูงใจจริง

ผลคือ **แบบฝึกหัดอิสระแบบสุ่มถูกเลื่อนออกไป** — ไม่เสียของ เพราะหน้าเล่นใช้โค้ดชุดเดียวกัน ต่างแค่ที่มาของรายการข้อ

`stages` / `stageClears` มี schema และ security rules ครบแล้วตั้งแต่ sub-project ข้อ 2 แต่**ยังไม่มีเครื่องมือฝั่งแอดมินแตะ collection เหล่านี้เลย** (หน้านำเข้า JSON และหน้าคลังเนื้อหาเขียนแค่ `exercises`) งานนี้จึงต้องสร้างหน้าแอดมินสำหรับด่านเพิ่มด้วย

## 2. ขอบเขต

### อยู่ในรอบนี้

- หน้าเลือกสกิล+เลเวล → หน้าเส้นทางด่าน → หน้าเล่นด่าน → หน้าสรุปผล+ดาว (ฝั่งนักเรียน)
- หน้ารายการด่าน + หน้าสร้าง/แก้ด่าน (ฝั่งแอดมิน)
- ตรวจคำตอบอัตโนมัติสำหรับ `mcq` และ `fill_blank`
- ระบบดาวและการปลดล็อกด่านถัดไป
- ทิศทางภาพของโซนนักเรียน + มาสคอต "น้องหยก"
- เนื้อหานำร่อง 1 สกิล × 1 เลเวล ~20 ข้อ / 3 ด่าน (= `PLAN.md` §15 ข้อ 4 ขยับเข้ามาอยู่ในงานนี้)
- งานแยกก้อนเล็กที่ทำก่อน: privacy/consent notice ในฟอร์ม onboarding (§12 ของ spec นี้)

### ไม่อยู่ในรอบนี้ (ระบุให้ชัดเพื่อไม่ให้เข้าใจผิดภายหลัง)

- ข้อชนิด `matching` (จับคู่) — ต้องออกแบบ UI จับคู่บนมือถือใหม่ทั้งชุด
- ข้อเขียนตอบ (`short_answer` / `paragraph`) + คิวตรวจงานของแอดมิน → core loop 2
- `shadowing`
- ปุ่ม "ℹ️ ดูสรุปไวยากรณ์" — **เว้นตำแหน่งไว้ในหน้าต่างข้อมูลก่อนเริ่มด่านแล้ว** แต่ยังไม่ต่อของจริง เพราะต้องมีเนื้อหา `grammarNotes` + เครื่องมือแอดมินก่อน
- แบบฝึกหัดอิสระแบบสุ่มจากคลัง
- การบ้านรายบุคคล/กลุ่ม
- streak และสถิติบน dashboard (มีแค่ดาวรวมบนหน้าเส้นทางด่าน)
- ท่ามาสคอต "เสียใจ" (ชีตที่มีตอนนี้เป็นท่าบวกทั้งหมด รอปิ๊กเจนเพิ่ม ใช้ท่าอื่นแทนไปก่อน)

### แตะของเดิมแค่จุดเดียว

เพิ่มปุ่ม "ไปฝึก" บน dashboard ให้เข้า `learn/index.html`

## 3. การตัดสินใจหลัก

| # | ตัดสินใจ | เหตุผล |
|---|---|---|
| 1 | หนึ่งรอบการเล่น = **ชุดโจทย์ (ด่าน)** ไม่ใช่โจทย์เดี่ยวไหลต่อเนื่อง | ให้ความรู้สึก "จบรอบ" แบบ Duolingo/Kahoot และทำให้เกณฑ์ดาว 100/70/40% ใน §6 มีความหมาย |
| 2 | **ดาวผูกกับด่าน** ไม่ใช่กับข้อ | `stageClears` มี doc id คงที่ `{uid}__{stageId}` ดาวจึงมีเพดาน 3 ต่อด่าน ไม่เฟ้อ เล่นซ้ำทับค่าเดิม |
| 3 | ตอบผิด → **เห็นเฉลยแล้วไปข้อถัดไป** ไม่ใช่ลองจนถูก | คะแนน = ถูก/จำนวนข้อ ตรงไปตรงมา ใช้กับ `passThreshold` และเกณฑ์ดาวได้ทันที · การลองใหม่ของระบบนี้คือ "เล่นด่านซ้ำเพื่อเก็บดาวให้ครบ" |
| 4 | ปลดล็อกด่านถัดไปเมื่อ **คะแนน ≥ `passThreshold`** (ค่าเริ่มต้น 0.7) | ฟิลด์มีอยู่ต่อด่านแล้ว ปิ๊กปรับเกณฑ์ด่านที่ยากเกินได้เอง · ด่านแรกของแต่ละสกิล+เลเวลเปิดเสมอ |
| 5 | ด่านรับเฉพาะ **`mcq` + `fill_blank`** | ตรงกับ §15 ข้อ 3 ("ทำ type เดียวให้สมบูรณ์ก่อน") และไม่กระทบเกณฑ์ดาวเพราะดาวคิดจากคะแนนทั้งด่าน |
| 6 | `fill_blank` ใช้ **word bank (กดเลือกคำ)** ไม่ใช่ช่องพิมพ์ · ตัวลวงดึงจาก**เฉลยของข้ออื่นในด่านเดียวกัน** | ปิ๊กขอ "ลดการพิมพ์ให้น้อยที่สุด" · ไม่ต้องแก้ schema ที่ทดสอบผ่านแล้ว · ถ้าวันหนึ่งอยากคุมตัวลวงเอง เติมฟิลด์ `distractors` ทีหลังได้โดยไม่ต้องรื้อหน้าเล่น |
| 7 | **ไม่บันทึกอะไรระหว่างเล่น** เขียนครั้งเดียวตอนจบด่านแบบ atomic | กันสถานะค้างครึ่งทางทั้งใน DB และใน UI · ด่านยาวแค่ 5–10 ข้อ ความเสี่ยงที่จะเสียเปล่าต่ำ |

### ดาวรวมคิดจากอะไร (ต้องไม่สับสน)

- **ดาวรวมที่โชว์ = `Σ starsFor(stageClears[i].score)`** เท่านั้น
- `submissions.bestStars` ยังถูกเขียนต่อข้อตามเดิม (เพราะ rules บังคับให้มีฟิลด์นี้ และเป็นข้อมูลที่ต้องใช้ทำ spaced repetition/จุดอ่อนทีหลัง) แต่ **ไม่ถูกนำมารวมเป็นดาวรวม** — ถ้านำมารวมด้วยจะกลายเป็นนับซ้ำ

## 4. ทิศทางภาพของโซนนักเรียน

ปิ๊กเลือกทิศทาง **"กระดาษสว่าง"** (ขาว/เขียวสด ปุ่มมีขอบล่างหนาให้รู้สึกกดได้ แบบ Duolingo) จาก 3 ทางเลือก เหตุผลที่ไม่เลือกแบบเวทีมืดสไตล์ Kahoot: แบบนั้นใช้สีสดไปกับการ์ดตัวเลือกจนเหลือสีเขียว/แดงบอกถูก-ผิดไม่ได้ ซึ่งเป็นหัวใจของการตรวจทันที

### ชุดสี (เพิ่มเข้า `src/styles/tokens.css`)

| token | ค่า | ใช้ทำอะไร |
|---|---|---|
| `--color-bg` | `#ffffff` | พื้นหลัง |
| `--color-text` | `#1f2933` | ตัวอักษรหลัก |
| `--color-primary` | `#37c871` | ปุ่มหลัก / ความคืบหน้า |
| `--color-primary-shadow` | `#26a058` | ขอบล่างของปุ่ม (ความรู้สึก "กดได้") |
| `--color-correct-bg` / `--color-correct-text` | `#e8f9ee` / `#17753c` | การ์ดที่ตอบถูก |
| `--color-wrong-bg` / `--color-wrong-text` | `#fdeaea` / `#a3181c` | การ์ดที่ตอบผิด |
| `--color-border` | `#dfe3e8` | ขอบการ์ดปกติ |
| `--color-star` | `#f5b91d` | ดาว |
| `--color-muted` | `#9aa5b1` | ข้อความรอง / ด่านที่ล็อก |

ฟอนต์: **Mitr** (Google Fonts, รองรับไทย ทรงกลมอ่านง่าย) ตั้งเป็น `--font-base` ทั้งเว็บ fallback เป็น `system-ui` ถ้าโหลดไม่ได้ ใช้ `font-display: swap` เพื่อไม่ให้หน้าค้างรอฟอนต์

**ผลข้างเคียงที่ตั้งใจให้เกิด:** `--color-primary` ปัจจุบันเป็นน้ำเงิน `#2563eb` และถูกใช้โดย `.btn-primary` ในหน้าแอดมินทุกหน้า การเปลี่ยนเป็นเขียวจึงทำให้**ปุ่มฝั่งแอดมินเปลี่ยนสีตามไปด้วย** — ตั้งใจให้เป็นเช่นนั้น เพื่อให้ทั้งเว็บใช้ชุดสีเดียวกัน ไม่ใช่นักเรียนเขียวแอดมินน้ำเงิน

### หน้าเล่นด่าน

หนึ่งคำถามต่อหนึ่งหน้าจอ · แถบความคืบหน้าด้านบน · การ์ดคำตอบ **กดได้ทั้งใบ** ออกแบบสำหรับนิ้วบนมือถือก่อนเมาส์ · ตรวจทันทีที่กด ไม่มีปุ่ม "ส่งคำตอบ" แยก · การ์ดที่ถูกเป็นเขียว ที่กดผิดเป็นแดง เห็นพร้อมกัน → ปุ่ม "ต่อไป"

### หน้าเส้นทางด่าน

**เส้นทางคดเคี้ยวแนวตั้ง** วาดด้วย SVG เป็นเส้นโค้งลากผ่านทุกด่านจริง — เส้นเทาคือทางทั้งหมด ส่วนที่ผ่านมาแล้วเป็นเขียวอ่อน เห็นความคืบหน้าเป็นภาพโดยไม่ต้องอ่านตัวเลข

วงกลมด่านแสดงแค่ **เลขด่าน + ป้ายดาวเล็ก** ไม่แบกชื่อหัวข้อ (ชื่อไวยากรณ์ยาวเกินกว่าจะใส่ในวงกลมได้) — **แตะที่ด่านแล้วเด้งหน้าต่างขึ้นจากด้านล่าง** บอกชื่อหัวข้อเต็ม จำนวนข้อ เกณฑ์ผ่าน ดาวที่เคยได้ และปุ่ม "เริ่มเล่น" · ด่านที่ล็อกเด้งหน้าต่างเดียวกันแต่เขียนว่าต้องทำอะไรถึงจะเปิด และไม่มีปุ่มเริ่ม (กันเด็กงงว่าทำไมกดไม่ได้)

หน้าต่างนี้คือที่ที่ปุ่ม "ℹ️ ดูสรุปไวยากรณ์" จะมาอยู่ในอนาคต

### มาสคอต "น้องหยก"

กระต่ายหยกสีเขียว **ใช้ไฟล์ภาพ PNG ไม่ใช่ SVG** (ลองวาด SVG แล้วสู้ความนุ่มของเส้นและการไล่แสงบนผิวหยกของต้นฉบับไม่ได้)

- ต้นแบบเก็บไว้ที่ `docs/design/mascot-reference.jpg` (character sheet 4 ท่า) และ `docs/design/mascot-poses-sheet.jpg` (ชีต 18 ท่า ตาราง 6×3)
- ต้องเขียนสคริปต์ `scripts/prepare-mascot.mjs` ตัดชีตเป็นไฟล์ย่อย → `src/assets/mascot/*.png` แล้ว **commit ไฟล์ที่ตัดแล้วเข้า repo** เพื่อให้ตอนรันเว็บไม่ต้องพึ่ง dependency ใดๆ
- เครื่องที่ใช้พัฒนาไม่มี ImageMagick / Pillow / numpy มีแต่ Node 24 → เพิ่ม **`sharp` เป็น devDependency** สำหรับสคริปต์นี้อย่างเดียว
- **ลบพื้นขาวด้วย flood fill จากขอบภาพเท่านั้น ห้ามแปลง "ทุกพิกเซลที่ขาว" เป็นโปร่ง** เพราะตัวมาสคอตมีแสงวาวสีขาวอยู่ข้างใน ถ้าทำผิดวิธีจะทะลุเป็นรู · ต้นฉบับเป็น JPEG จึงมีขอบฟุ้ง ให้เผื่อ tolerance และกัดขอบ alpha เล็กน้อย
- ข้ามท่าที่มีตัวหนังสืออังกฤษบนภาพ (GOAL! / FIGHT!) เพราะแอปเป็นภาษาไทย
- โมดูล `src/lib/mascot.js` แปลงชื่ออารมณ์ (`normal` / `correct` / `wrong` / `clear`) เป็น path ของไฟล์ — ทุกหน้าเรียกผ่านโมดูลนี้เท่านั้น เพื่อให้เปลี่ยนชุดภาพทีหลังแก้ไฟล์เดียว

## 6. โมดูล

### ตรรกะบริสุทธิ์ (ไม่แตะ Firestore — ทดสอบด้วย vitest ตรงๆ)

| ไฟล์ | หน้าที่ |
|---|---|
| `src/lib/grading.js` | ตรวจคำตอบต่อข้อ → คะแนน 0–1 · `starsFor(score)` ตามเกณฑ์ §6 · รวมคะแนนของด่าน |
| `src/lib/stage-session.js` | state machine ของการเล่น: คิวข้อ ข้อปัจจุบัน ผลแต่ละข้อ สรุปผลตอนจบ |
| `src/lib/word-bank.js` | สร้างตัวเลือกให้ `fill_blank` จากเฉลยข้ออื่นในด่าน + สับตำแหน่ง |
| `src/lib/stage-progress.js` | จาก `stageClears` → ด่านไหนปลดล็อก ได้กี่ดาว รวมกี่ดาว |
| `src/lib/stage-form.js` | ตรรกะฟอร์มสร้างด่านฝั่งแอดมิน (ล้อ `exercise-form.js`) |
| `src/lib/mascot.js` | อารมณ์ → path ของไฟล์ภาพ |

### คุยกับ Firestore (แยกออกจากตรรกะเสมอ)

| ไฟล์ | หน้าที่ |
|---|---|
| `src/lib/stage-io.js` | อ่าน/เขียน `stages`, อ่าน `stageClears` ของผู้ใช้ |
| `src/lib/submission-io.js` | อ่าน submissions เดิม + เขียนผลจบด่านแบบ batch |

เหตุผลที่แยกละเอียดขนาดนี้: แพตเทิร์น "ตรรกะบริสุทธิ์ + I/O แยกไฟล์" จาก sub-project ที่แล้วทำให้เทสเร็วและไฟล์ไม่บวม อันนี้ทำต่อจากของเดิม ไม่ได้คิดใหม่

## 7. การไหลของข้อมูล

### โหลดด่าน

1. `getDoc(stages/<id>)` → ได้ `itemIds` (สูงสุด 20 ตาม schema)
2. `query(exercises, where(documentId(), 'in', itemIds))` — ลิมิตของ `in` คือ 30 ต่อ query เพราะฉะนั้น 20 ข้อจบใน query เดียว แล้ว**เรียงกลับตามลำดับใน `itemIds`** เพราะ Firestore ไม่รับประกันลำดับผลลัพธ์
3. โหลดทีละด่านแบบนี้ตรงกับ `PLAN.md` §12 ข้อ (3) ที่ห้าม query ทั้งคลังมาเก็บไว้ในเครื่อง

### ระหว่างเล่น

ไม่เขียนฐานข้อมูลเลยสักครั้ง สถานะอยู่ในหน่วยความจำล้วน

### ตอนจบด่าน — จุดที่ต้องระวังเรื่อง security rules

`firestore.rules` ของ `submissions` บังคับว่า `bestStars` ห้ามลดลง (`request.resource.data.bestStars >= resource.data.bestStars`) และห้ามแก้ `uid` / `exerciseId` / `createdAt`

**ถ้าเขียนทับด้วย `setDoc` ตรงๆ แล้วรอบนี้เด็กทำได้แย่กว่าเดิม rules จะปฏิเสธ และเพราะเป็น `writeBatch` มันจะล้มทั้งชุด เด็กเสียผลทั้งด่านทั้งที่ตอบถูกไปหลายข้อ**

ทางแก้ — **อ่านก่อนเขียนเสมอ** เพิ่ม 1 query ก่อน batch:

```
query(submissions, where(documentId(),'in',[ทุก submissionId ของข้อในด่านนี้]))
  bestStars    = max(ของเดิม, ของรอบนี้)
  attemptCount = ของเดิม + 1
  wrongCount   = ของเดิม + (รอบนี้ตอบผิดไหม ? 1 : 0)
  createdAt    = ของเดิม (ถ้าเคยมี) ไม่งั้นเวลาปัจจุบัน
```

doc id ใช้ `submissionId(uid, exerciseId)` ที่มีอยู่แล้ว → `{uid}__bank__{exerciseId}` (ไม่ใช่การบ้าน จึงเป็น scope `bank`)

**ทำไมไม่ต้องใส่ `where('uid','==',me)` ในคิวรีนั้น:** doc id มี uid ของเจ้าของฝังอยู่แล้ว เอกสารที่ query ได้จึงเป็นของตัวเองเสมอ (ถ้าใส่ทั้งสองเงื่อนไขจะกลายเป็นคิวรีผสมที่อาจต้องสร้าง composite index เพิ่มโดยไม่จำเป็น)

จากนั้น `writeBatch` เขียนทีเดียวแบบ atomic: submissions ต่อข้อ + `stageClears/{uid}__{stageId}` รวมไม่เกิน 21 writes (ลิมิต 500)

### `stageClears` เขียนเมื่อไหร่

- เขียน **ทุกครั้งที่เล่นจบ ไม่ว่าจะผ่านเกณฑ์หรือไม่** เพราะมันคือที่เก็บ "คะแนนดีที่สุดที่เคยทำได้" ซึ่งเป็นที่มาของดาว (ได้ 50% ก็ได้ 1 ดาว แม้ยังไม่ผ่านเกณฑ์ 70%)
- "ผ่านแล้ว" เป็น**ค่าคำนวณตอนแสดงผล** (`score >= passThreshold`) ไม่ใช่ฟิลด์ที่เก็บ
- เขียนทับเฉพาะเมื่อคะแนนดีขึ้น — rules ไม่ได้บังคับข้อนี้ เราคุมฝั่ง client ซึ่งอยู่ในระดับความเสี่ยงที่ `PLAN.md` §12 ยอมรับไว้แล้ว (โกงได้แค่คะแนนตัวเอง ไม่ได้ข้าม tier)

### สองกรณีพังที่ต้องรองรับตั้งแต่แรก

- **บันทึกไม่สำเร็จ (เน็ตหลุด)** — โชว์หน้าสรุปตามปกติพร้อมแถบ "ยังบันทึกผลไม่ได้" + ปุ่มลองใหม่ ผลยังอยู่ในหน่วยความจำ · ไม่ใช้ offline persistence ของ Firestore เพราะเพิ่มความซับซ้อนเกินจำเป็น
- **tier `free` เจอด่านที่ข้อไม่ใช่ preview** — rules จะคืนข้อมาไม่ครบโดยไม่ error ต้องเช็กจำนวนที่ได้เทียบกับ `itemIds` แล้วขึ้นข้อความ "ด่านนี้ยังไม่เปิดสำหรับบัญชีของคุณ" ไม่ใช่ปล่อยให้เล่นด่านแหว่ง

### ออกกลางด่าน

ไม่บันทึกอะไรเลย และถามยืนยันก่อนออก ("ออกตอนนี้ความคืบหน้าจะหาย") — ไม่ทำ resume เพราะต้องเก็บสถานะค้างครึ่งทางใน Firestore ซึ่งบวมทั้ง schema ทั้ง rules ทั้ง UI เพื่อแลกกับกรณีที่ด่านยาวแค่ 5–10 ข้อ

## 8. การตรวจคำตอบ และ word bank

### การตรวจ

- `mcq` — คำตอบตรงกับ `answerKey[0]` → 1 ไม่ตรง → 0
- `fill_blank` — `answerKey` เป็น array ของคำตอบที่ยอมรับได้ ตรงกับตัวใดตัวหนึ่ง → 1
- **การเทียบข้อความ:** ตัดช่องว่างหน้า-หลัง ยุบช่องว่างซ้ำ ไม่สนตัวพิมพ์เล็ก-ใหญ่ และทำ `'` กับ `'` ให้เป็นตัวเดียวกัน · **ไม่ตัดเครื่องหมายวรรคตอนทิ้ง** เพราะบางข้อจุดสำคัญอยู่ที่เครื่องหมายนั้น
- คะแนนของด่าน = จำนวนข้อที่ถูก ÷ จำนวนข้อทั้งหมด
- `starsFor(score)`: `= 1.0` → 3 · `>= 0.7` → 2 · `>= 0.4` → 1 · ต่ำกว่านั้น → 0 · **เทียบแบบเผื่อค่าปัดเศษ** (7/10 ต้องไม่กลายเป็น 0.6999… แล้วตกเกณฑ์)

### word bank

1. ตัวลวงมาจาก **เฉลยของข้อ `fill_blank` อื่นในด่านเดียวกัน** (คำระดับเดียวกัน หัวข้อเดียวกันโดยธรรมชาติ)
2. **ตัดคำที่บังเอิญเป็นคำตอบที่ยอมรับได้ของข้อนี้ออก** — ถ้าข้อนี้รับทั้ง `doesn't` และ `does not` แล้วอีกข้อเฉลยว่า `does not` พอดี มันจะกลายเป็นตัวลวงที่กดแล้วขึ้นว่าผิดทั้งที่ถูก
3. ถ้ายังไม่ครบ 3 ตัว → ดึง `choices` จากข้อ `mcq` ในด่านเดียวกันมาเสริม
4. ถ้ายังไม่พออีก → แสดงเท่าที่มี (ขั้นต่ำ 2 ใบ) **และหน้าสร้างด่านต้องเตือนปิ๊กตั้งแต่ตอนสร้าง** — แก้ตอนสร้างดีกว่าปล่อยให้เด็กเจอข้อที่มีตัวเลือก 2 ใบแล้วเดาถูก 50%
5. **การสับตำแหน่ง** รับฟังก์ชันสุ่มเป็น parameter (ใช้จริงส่ง `Math.random` เทสส่งตัวสุ่มแบบ seed) และ**สับใหม่ทุกครั้งที่เล่นโดยตั้งใจ** เพื่อไม่ให้เด็กจำว่า "ข้อนี้กดใบที่สาม" แทนการจำคำตอบ

## 9. หน้าสร้างด่าน (`admin/stage.html`)

หยิบโจทย์จากคลังโดยกรองตามสกิล/เลเวล/แท็ก ติ๊กเลือก จัดลำดับด้วยปุ่มขึ้น-ลง · ตั้งชื่อด่าน ลำดับที่ `passThreshold` (ค่าเริ่มต้น 0.7) `isPreview` และสถานะอนุมัติ

### กฎที่ต้องกันไว้ — ทั้งหมดคือข้อที่ถ้าไม่กัน เด็กจะเป็นคนเจอปัญหาแทน

| กฎ | ระดับ |

| รับเฉพาะข้อชนิด `mcq` / `fill_blank` | **บล็อก** |
| จำนวนข้อ 1–20 ตาม schema | **บล็อก** |

| ลำดับด่านซ้ำกับด่านอื่นในสกิล+เลเวลเดียวกัน | เตือน |
| มีข้อเติมคำที่หาตัวลวงได้ไม่ครบ 3 ตัว | เตือน |

## 10. เนื้อหานำร่อง

**ไวยากรณ์ ระดับ A2 ประมาณ 20 ข้อ ทำเป็น 3 ด่าน** ตามแท็กที่มีใน `taxonomy.js` อยู่แล้ว เรียงตามลำดับที่สอนกันจริง:

1. `past-simple` — Past Simple (regular + irregular)
2. `past-continuous` — Past Continuous
3. `present-perfect` — Present Perfect (ประสบการณ์)

ขั้นตอน: ผมค้นคว้าและร่าง → ปิ๊กตรวจ/แก้บนหน้าเว็บ (`admin/exercise.html` และหน้าคลังเนื้อหา) → นำเข้าผ่านหน้า import JSON ที่มีอยู่ → อนุมัติ → สร้างด่าน

**หมายเหตุสำคัญ:** นี่จะเป็นการเขียนข้อมูลลง Firestore production ครั้งแรกของโปรเจกต์ (ที่ผ่านมาทดสอบบน emulator อย่างเดียว) จึงเป็นการพิสูจน์ batch write ผ่าน rules จริงไปในตัว

**การ generate เนื้อหาจำนวนมากยังคงเป็น session แยกต่างหาก** ตามที่ `PLAN.md` §15 เตือนไว้ว่าปนกับ session เขียนโค้ดแล้วคุณภาพตก

## 11. การทดสอบ

- **Unit (vitest)** — `grading` (ทุกชนิดข้อ, การเทียบข้อความ, เกณฑ์ดาวที่ขอบ 40%/70%/100%), `word-bank` (ตัดคำที่เป็นคำตอบของข้อตัวเอง, ตัวลวงไม่พอ, สับแบบ seed), `stage-session`, `stage-progress` (ปลดล็อก/ดาวรวม), `stage-form` (กฎ validation ทุกข้อ)
- **Rules test (emulator)** — เพิ่มเคสตามโฟลว์จริง: batch เขียน submissions + stageClear พร้อมกัน, เคสที่ `bestStars` ลดลงต้องถูกปฏิเสธ, นักเรียนเขียน `stageClears` ของคนอื่นไม่ได้, นักเรียน tier `free` อ่านด่าน/ข้อที่ไม่ใช่ preview ไม่ได้
- **ทดสอบจริง** — ปิ๊กเล่นจบด่านบนเว็บจริงด้วยบัญชีตัวเอง

## 13. ความเสี่ยงและของค้าง

- **ยังไม่มีท่ามาสคอต "เสียใจ"** — ชีต 18 ท่าที่มีเป็นท่าบวกทั้งหมด ต้องเจนเพิ่มหรือใช้ท่าขี้อายแทนไปก่อน
- **การตัดพื้นขาวจากภาพ JPEG จะมีขอบฟุ้งเล็กน้อย** — ยอมรับได้บนพื้นขาวของแอป แต่ถ้าวางบนพื้นสีจะเห็น ให้ระวังตอนวางมาสคอตบนปุ่มหรือแถบสี
- **ยังไม่เคยทดสอบการสลับ tier กับบัญชีจริง** — ทั้ง 2 บัญชีของปิ๊กเป็น `role: admin` หน้าจัดการผู้ใช้จึงว่าง (กรอง `role == "student"`) เคส tier `free` จะทดสอบได้จริงก็ต่อเมื่อมีนักเรียนคนแรกสมัคร
- `auth-guard.js` `requireLogin` ยังแสดงข้อความผิดเมื่อ Firestore ล่มชั่วคราว (ค้างจาก foundation spec §12)
